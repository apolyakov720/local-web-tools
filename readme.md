# local-web-tools

Локальный стенд для тестирования веб-сервисов на реальном iPhone: собственный DNS, доверенный HTTPS и обратный прокси.

Тестируемый сервис запускается отдельно любым подходящим способом. Стенд запускает CoreDNS и Caddy и предоставляет доступ к сервису по постоянному HTTPS-адресу внутри локальной сети.

## Как устроен стенд

~~~text
iPhone в локальной сети
  │
  ├─ DNS: myapp.test → IP компьютера
  │       CoreDNS, UDP/TCP 53
  │
  └─ HTTPS: https://myapp.test/
          Caddy, TCP 443
            │
            └─ HTTP: http://127.0.0.1:8080
                    целевой HTTP/HTTPS-сервис

Дополнительно:
http://myapp.test/rootCA.crt → публичный сертификат CA, TCP 80
~~~

`localhost` на iPhone обозначает сам телефон. Поэтому телефон обращается к компьютеру по имени `myapp.test`, а Caddy передаёт запросы адресу из `AppUpstream`.

В инструкции используются условные значения для примеров:

| Параметр | Пример |
|---|---|
| DNS-имя приложения | `myapp.test` |
| IP компьютера | `192.168.0.124` |
| Локальная подсеть | `192.168.0.0/24` |
| DNS роутера | `192.168.0.1` |
| Адрес целевого сервиса | `http://127.0.0.1:8080` |

Замените сетевые значения на свои в `config.psd1`.

## Зависимости и версии

Инструкция рассчитана на Windows x64 и PowerShell 7. Для установки используются следующие версии инструментов:

| Зависимость | Версия | Назначение |
|---|---|---|
| PowerShell | `7` | Выполнение скриптов и управление процессами |
| Caddy | `2.11.7` | HTTP-раздача сертификата и HTTPS-прокси |
| CoreDNS | `1.15.0` | Разрешение имени приложения и пересылка остальных DNS-запросов |
| mkcert | `1.4.4` | Создание локального CA и сертификата приложения |

Также необходимы:

- компьютер и iPhone в одной локальной сети с доступом устройств друг к другу; компьютер может быть подключён к роутеру по Ethernet, а телефон — по Wi-Fi;
- права администратора Windows для настройки брандмауэра;
- запущенный HTTP/HTTPS-сервис, доступный с компьютера;
- зависимости целевого сервиса — согласно его документации.

Docker Desktop требуется только в случае запуска целевого сервиса в контейнере. VPN и изоляция клиентов Wi-Fi могут влиять на доступность компьютера с телефона.

PowerShell 7 устанавливается отдельно: [официальная инструкция Microsoft](https://learn.microsoft.com/en-us/powershell/scripting/install/installing-powershell-on-windows).

## Установка зависимостей

Исполняемые файлы сторонних программ устанавливаются вручную. Они не поставляются с проектом и исключены из Git. Скрипты не скачивают их автоматически.

### Caddy

Скачайте стандартную сборку для **Windows amd64**:

- [официальная страница скачивания Caddy](https://caddyserver.com/download);
- [релиз Caddy 2.11.7](https://github.com/caddyserver/caddy/releases/tag/v2.11.7).

Страница скачивания может выдавать более новую сборку. После установки проверьте фактическую версию.

Распакуйте или переименуйте исполняемый файл так, чтобы он находился здесь:

~~~text
tools/
└── caddy/
    ├── Caddyfile    ← конфигурация поставляется с проектом
    └── caddy.exe   ← скачивается самостоятельно
~~~

Сохраните существующий `Caddyfile`. Для этого стенда достаточно стандартных модулей Caddy. Устанавливать Caddy службой Windows или добавлять его в `PATH` не требуется: скрипты используют локальный файл.

Проверка из корня проекта:

~~~powershell
.\tools\caddy\caddy.exe version
~~~

Ожидаемая версия: `v2.11.7`.

### CoreDNS

Скачайте сборку для **Windows amd64**:

- [релиз CoreDNS 1.15.0](https://github.com/coredns/coredns/releases/tag/v1.15.0);
- [архив coredns_1.15.0_windows_amd64.zip](https://github.com/coredns/coredns/releases/download/v1.15.0/coredns_1.15.0_windows_amd64.zip).

Распакуйте `coredns.exe` в каталог `tools\coredns`:

~~~text
tools/
└── coredns/
    ├── Corefile      ← конфигурация поставляется с проектом
    └── coredns.exe   ← скачивается самостоятельно
~~~

Сохраните существующий `Corefile`. Регистрация службы и изменение `PATH` не нужны.

Проверка:

~~~powershell
.\tools\coredns\coredns.exe -version
~~~

Ожидаемая версия: `CoreDNS-1.15.0`.

### mkcert

Установите **mkcert 1.4.4**:

- [релиз mkcert 1.4.4](https://github.com/FiloSottile/mkcert/releases/tag/v1.4.4);
- [mkcert-v1.4.4-windows-amd64.exe](https://github.com/FiloSottile/mkcert/releases/download/v1.4.4/mkcert-v1.4.4-windows-amd64.exe);
- [официальная инструкция установки](https://github.com/FiloSottile/mkcert#installation).

При ручной установке переименуйте файл в `mkcert.exe` и добавьте содержащую его папку в пользовательскую переменную Windows `Path`. Допустимо хранить его в `tools\mkcert`, но полный путь к этой папке всё равно должен быть в `Path`.

Чтобы изменить `Path`, найдите в Windows «Изменение переменных среды текущего пользователя», откройте `Path`, добавьте каталог mkcert и откройте новое окно PowerShell.

В отличие от Caddy и CoreDNS, текущие скрипты вызывают mkcert по имени команды, поэтому одного наличия `tools\mkcert\mkcert.exe` недостаточно. Исполняемый файл mkcert также не включается в Git.

Проверка:

~~~powershell
Get-Command mkcert
mkcert -version
~~~

Ожидаемая версия: `v1.4.4`.

## Настройки: config.psd1

Все изменяемые параметры стенда задаются в одном файле:

~~~powershell
@{
    Domain = 'myapp.test'

    LanIp         = '192.168.0.124'
    AllowedSubnet = '192.168.0.0/24'

    DnsForwarders = @('192.168.0.1')
    AppUpstream = 'http://127.0.0.1:8080'

    DnsTtl = 60
}
~~~

| Параметр | Описание |
|---|---|
| `Domain` | Имя приложения без протокола, порта и пути. Из него строится HTTPS-адрес и имена файлов сертификата |
| `LanIp` | IP компьютера, доступный с iPhone. Используется в DNS-записи, привязке серверов и брандмауэре |
| `AllowedSubnet` | Подсеть, из которой разрешены входящие подключения. При маске `255.255.255.0` и адресах `192.168.0.x` это `192.168.0.0/24` |
| `DnsForwarders` | Массив вышестоящих DNS-серверов, например DNS домашнего роутера. Не указывайте здесь собственный CoreDNS, чтобы не создать цикл пересылки |
| `AppUpstream` | HTTP/HTTPS-адрес целевого сервиса, которому Caddy передаёт запросы |
| `DnsTtl` | Время кеширования локальной DNS-записи в секундах |

### Как получить значения для config.psd1

Сетевые значения берутся из настроек Windows, а имя приложения, его адрес и TTL выбираются для конкретного стенда. Команды ниже только читают информацию и не меняют сетевые настройки.

#### LanIp: IP компьютера в локальной сети

Посмотрите IPv4-адреса активных подключений:

~~~powershell
Get-NetIPAddress -AddressFamily IPv4 |
    Where-Object { $_.AddressState -eq 'Preferred' } |
    Format-Table InterfaceAlias, IPAddress, PrefixLength -AutoSize
~~~

Пример вывода:

~~~text
InterfaceAlias                     IPAddress       PrefixLength
--------------                     ---------       ------------
Ethernet                           192.168.0.124              24
CorporateVPN                       10.2.9.10                  32
vEthernet (WSL (Hyper-V firewall))  172.23.112.1                20
Loopback Pseudo-Interface 1         127.0.0.1                    8
~~~

Выберите подключение к тому же роутеру, через который iPhone выходит в Wi-Fi: обычно это `Ethernet` или `Wi-Fi`. При необходимости посмотреть описания адаптеров:

~~~powershell
Get-NetAdapter |
    Format-Table Name, InterfaceDescription, Status -AutoSize
~~~

Для примера выше:

~~~powershell
LanIp = '192.168.0.124'
~~~

Адреса корпоративного VPN, WSL, Docker и loopback для этого сценария не подходят: телефону нужен доступный адрес компьютера в домашней или офисной LAN. Наличие нескольких маршрутов по умолчанию при VPN само по себе не определяет нужный интерфейс.

Проверьте IP и маску телефона в **Настройки → Wi-Fi → ⓘ возле текущей сети**. Например, при маске `255.255.255.0` телефон `192.168.0.152` и компьютер `192.168.0.124` относятся к одной подсети.

В следующих командах замените `Ethernet` на выбранное имя подключения, если оно отличается. Имя интерфейса используется только для получения информации, сохранять его в `config.psd1` не нужно. [Описание Get-NetIPAddress](https://learn.microsoft.com/en-us/powershell/module/nettcpip/get-netipaddress).

#### AllowedSubnet: адрес локальной подсети

В предыдущем выводе `PrefixLength` обозначает длину сетевого префикса: например, `24` соответствует маске `255.255.255.0`.

Чтобы получить адрес самой подсети без ручного расчёта, посмотрите локальные маршруты выбранного интерфейса:

~~~powershell
Get-NetRoute -InterfaceAlias 'Ethernet' -AddressFamily IPv4 |
    Where-Object {
        $_.NextHop -eq '0.0.0.0' -and
        $_.DestinationPrefix -notmatch '/32$|^224\.'
    } |
    Format-Table InterfaceAlias, DestinationPrefix, NextHop -AutoSize
~~~

Пример результата:

~~~text
InterfaceAlias DestinationPrefix NextHop
-------------- ----------------- -------
Ethernet       192.168.0.0/24     0.0.0.0
~~~

Перенесите подходящий `DestinationPrefix` в конфигурацию:

~~~powershell
AllowedSubnet = '192.168.0.0/24'
~~~

Если маршрутов несколько, выберите локальную подсеть, содержащую выбранный `LanIp` и адрес iPhone. `NextHop = 0.0.0.0` здесь обозначает непосредственно подключённую сеть, а не значение DNS-сервера.

Не подставляйте `/24` автоматически для любой сети. Например, для IP `192.168.1.124` с префиксом `23` сеть будет `192.168.0.0/23`. Используйте фактический префикс маршрута. [Описание Get-NetRoute](https://learn.microsoft.com/en-us/powershell/module/nettcpip/get-netroute).

#### DnsForwarders: куда пересылать остальные DNS-запросы

Получите IPv4 DNS-серверы выбранного LAN-подключения:

~~~powershell
Get-DnsClientServerAddress -InterfaceAlias 'Ethernet' -AddressFamily IPv4 |
    Select-Object -ExpandProperty ServerAddresses
~~~

Если команда вернула `192.168.0.1`, укажите:

~~~powershell
DnsForwarders = @('192.168.0.1')
~~~

Если для этого подключения настроено несколько подходящих серверов, сохраните их массивом:

~~~powershell
DnsForwarders = @('192.168.0.1', '192.168.0.2')
~~~

Второй адрес в примере используйте только при наличии такого DNS-сервера в своей сети. Адрес DNS не обязательно совпадает со шлюзом роутера — берите его из результата команды.

Для проверки конкретного сервера:

~~~powershell
Resolve-DnsName -Name example.com -Type A -Server 192.168.0.1 -DnsOnly
~~~

Ожидаем ответ с адресом сайта. Этот тест проверяет доступность сервера с компьютера.

Не используйте `LanIp`, на котором будет работать CoreDNS, в качестве его же вышестоящего DNS. Не объединяйте DNS разных корпоративных VPN с домашними серверами без настройки маршрутизации доменов: один сервер может знать внутреннее имя, а другой — возвращать отсутствие такого имени. Для базового стенда используйте DNS выбранной LAN.

#### Domain: имя, по которому iPhone откроет приложение

Это значение выбирается для стенда, а не получается из IP-настроек Windows. Пример:

~~~powershell
Domain = 'myapp.test'
~~~

Указывайте только DNS-имя: без `http://`, `https://`, порта и завершающего `/`. Файл сертификата будет создан для этого имени, а локальная DNS-запись свяжет его с `LanIp`.

Для выбранного значения внешний адрес сервиса — `https://myapp.test/`. При смене имени потребуется новый сертификат. Если сервис ограничивает допустимые имена хоста, добавьте выбранное имя в его настройки.

#### AppUpstream: адрес целевого HTTP/HTTPS-сервиса

Возьмите URL из вывода команды запуска сервиса или конфигурации его веб-сервера. Например, для сервиса по адресу `http://localhost:8080/`:

~~~powershell
AppUpstream = 'http://127.0.0.1:8080'
~~~

Для nginx в Docker посмотрите опубликованные порты:

~~~powershell
docker ps --format 'table {{.Names}}\t{{.Ports}}'
~~~

Например, запись `127.0.0.1:8443->443/tcp` означает, что порт `8443` на компьютере направлен на порт `443` контейнера. Если nginx на этом порту обслуживает HTTPS, укажите:

~~~powershell
AppUpstream = 'https://127.0.0.1:8443'
~~~

Используйте порт компьютера слева от `->`. Если отображается только `443/tcp` без опубликованного адреса и порта, этого недостаточно для подключения с хоста через `127.0.0.1:8443`. [Описание docker ps](https://docs.docker.com/reference/cli/docker/container/ls/).

Проверьте открытие выбранного URL на компьютере. Доступность TCP-порта можно дополнительно проверить так:

~~~powershell
Test-NetConnection -ComputerName 127.0.0.1 -Port 8443 -InformationLevel Quiet
~~~

`True` подтверждает доступность порта, но не корректность HTTP-ответов и TLS-сертификата. Выбирайте `http` или `https` по настройкам сервера, а не только по номеру порта.

При HTTPS upstream Caddy должен доверять сертификату nginx и успешно проверить имя или IP в сертификате. Настроенное на iPhone доверие к `myapp.test` относится к другому соединению — от телефона к Caddy.

В `AppUpstream` указывается внутренний адрес целевого сервиса. Им может быть веб-интерфейс, API или сервер статических файлов. Сервис должен быть запущен отдельно; внешний адрес `https://myapp.test/` используется для подключения через стенд.

#### DnsTtl: время кеширования локальной записи

Это выбранный параметр стенда; получать его из Windows не требуется. Для начала оставьте:

~~~powershell
DnsTtl = 60
~~~

Значение задаётся числом в секундах. TTL 60 подходит для разработки, когда IP компьютера может меняться. После изменения адреса ранее полученный DNS-ответ может оставаться в кеше до истечения своего TTL.

#### Проверка заполненного файла

После редактирования проверьте, что PowerShell читает конфигурацию:

~~~powershell
Import-PowerShellDataFile -LiteralPath .\config.psd1
~~~

Команда покажет значения настроек. Затем выполните подготовку сертификата и брандмауэра и запустите стенд по следующему разделу. Для уже настроенного стенда порядок действий после смены IP, DNS или домена приведён в разделе «Изменение сети и других параметров».

Загрузчик `env_load_config.ps1` читает настройки и создаёт переменные `DOMAIN`, `LAN_IP`, `ALLOWED_SUBNET`, `DNS_FORWARDERS`, `DNS_TTL` и `APP_UPSTREAM` в окружении текущего процесса. Caddy и CoreDNS получают их при запуске. Глобальные переменные Windows и DNS самого компьютера скрипты не меняют.

Имя `myapp.test` разрешается локальным DNS; покупать домен для этого примера не требуется. Утилиты не изменяют настройки целевого сервиса автоматически.

## Первая подготовка компьютера

Примеры команд ниже выполняются из корня проекта — каталога, содержащего `startup.ps1` и `config.psd1`. Откройте PowerShell в этом каталоге.

### 1. Установите зависимости и заполните config.psd1

Проверьте версии трёх инструментов и замените сетевые параметры на свои. Конфигурации `Caddyfile` и `Corefile` вручную редактировать для смены IP не требуется.

### 2. Создайте CA и сертификат приложения

Выполните под своей обычной учётной записью Windows:

~~~powershell
.\scripts\mkcert_install.ps1
.\scripts\mkcert_create.ps1
~~~

Первый скрипт создаёт локальный центр сертификации, если его нет, и устанавливает доверие к нему на компьютере. Второй читает `config.psd1` и выпускает сертификат для `Domain`.

При `Domain = 'myapp.test'` появятся:

~~~text
.local/certs/myapp.test.pem
.local/certs/myapp.test-key.pem
~~~

Не требуется выполнять эти команды при каждом запуске. Повторный выпуск нужен, например, после смены домена или истечения срока сертификата.

CA хранится отдельно от проекта; его каталог показывает `mkcert -CAROOT`. Подготовку сертификатов выполняйте от одной учётной записи, чтобы использовать один и тот же CA. [Описание работы mkcert](https://github.com/FiloSottile/mkcert).

### 3. Подготовьте сертификат для iPhone

~~~powershell
.\scripts\caddy_prepare.ps1
~~~

Скрипт создаёт каталоги `.local/public` и `.local/logs` и копирует публичный сертификат CA:

~~~text
$(mkcert -CAROOT)/rootCA.pem → .local/public/rootCA.crt
~~~

Именно `rootCA.crt` устанавливается на телефон. Это сертификат CA, подписавшего сертификат приложения.

Закрытые ключи `rootCA-key.pem` и `myapp.test-key.pem` остаются на компьютере. Их не нужно переносить на телефон или помещать в `.local/public`.

### 4. Настройте брандмауэр

Откройте отдельный PowerShell **от имени администратора**, перейдите в корень проекта и выполните:

~~~powershell
.\scripts\firewall_prepare.ps1
~~~

Скрипт самостоятельно загружает `config.psd1`. Он разрешает телефону подключаться к локальным сервисам:

| Правило | Протокол и порт | Для чего |
|---|---|---|
| `PwaLocalTools-DNS-UDP` | UDP 53 | Обычные DNS-запросы |
| `PwaLocalTools-DNS-TCP` | TCP 53 | DNS поверх TCP |
| `PwaLocalTools-HTTP` | TCP 80 | Скачивание публичного сертификата |
| `PwaLocalTools-HTTPS` | TCP 443 | Открытие приложения через HTTPS |

Доступ ограничен `LanIp`, подсетью `AllowedSubnet` и соответствующим `.exe`. Сам брандмауэр не отключается.

Если правило уже существует, скрипт обновляет его. Поэтому его нужно повторно выполнять после смены IP, подсети или расположения проекта. Этот шаг необходим: доступность сервиса с самого компьютера ещё не означает, что Windows пропустит запрос от телефона.

Для просмотра настроенных адресов:

~~~powershell
Get-NetFirewallRule -Name 'PwaLocalTools-*' |
    Get-NetFirewallAddressFilter |
    Select-Object LocalAddress, RemoteAddress
~~~

Брандмауэр настраивается отдельно; `startup.ps1` не меняет его правила при каждом запуске.

### 5. Запустите целевой сервис

Запустите сервис способом, указанным в его документации: командой разработки, отдельным веб-сервером или контейнером. Проверьте на компьютере доступность URL из `AppUpstream` и оставьте сервис работающим.

### 6. Запустите стенд

В обычном PowerShell из корня проекта:

~~~powershell
.\startup.ps1
~~~

Скрипт:

1. Загружает `config.psd1` в окружение.
2. Создаёт `.local/dns/hosts.txt` с актуальными IP и именем.
3. Проверяет Caddyfile и файлы сертификатов через `caddy validate`.
4. Запускает CoreDNS и Caddy в фоне.
5. Показывает PID процессов и адрес приложения.
6. Следит за завершением процессов; при выходе одного останавливает второй.

Окно `startup.ps1` должно оставаться открытым. Для штатной остановки нажмите **Ctrl+C**: блок `finally` остановит созданные этим запуском процессы.

PID подтверждает создание процесса, но не полную готовность сервиса. При первом запуске дайте серверам завершить инициализацию и проверьте DNS во втором окне:

~~~powershell
nslookup -type=A myapp.test. 192.168.0.124
nslookup -type=A example.com. 192.168.0.124
~~~

Замените имя и IP, если они отличаются в вашей конфигурации. Первый запрос должен вернуть `LanIp`; второй проверяет пересылку DNS. Точка после имени задаёт полное DNS-имя.

После этого переходите к настройке iPhone.

## Первое подключение iPhone

### 1. Подключитесь к нужной Wi-Fi-сети

Телефон должен видеть LAN-адрес компьютера. Для примера компьютер `192.168.0.124` и iPhone `192.168.0.152` находятся в одной подсети с маской `255.255.255.0`.

На компьютере должны работать `startup.ps1` и веб-сервер приложения. Для скачивания сертификата достаточно запущенного стенда: файл раздаёт сам Caddy.

### 2. Укажите локальный DNS в настройках Wi-Fi

Сначала задайте DNS, потому что адрес скачивания `myapp.test` обслуживается нашим CoreDNS.

На iPhone:

1. Откройте **Настройки → Wi-Fi**.
2. Нажмите **ⓘ** рядом с подключённой сетью.
3. Откройте **Настройка DNS**.
4. Выберите **Вручную**.
5. Удалите существующие серверы из списка.
6. Добавьте IP компьютера из `LanIp`, например `192.168.0.124`.
7. Нажмите **Сохранить**.

Не вводите `https://`, имя приложения или номер порта в поле DNS. IP самого телефона и режим получения его адреса менять не требуется.

На время тестирования оставьте только наш DNS. Обычные имена он пересылает серверам из `DnsForwarders`; второй DNS роутера не знает локальную запись `myapp.test`.

Настройка действует для выбранной Wi-Fi-сети. Если на телефоне используется VPN или отдельный DNS-профиль, он может влиять на разрешение имени. [Порядок ручной настройки DNS на iOS](https://developers.cloudflare.com/1.1.1.1/setup/ios/).

### 3. Скачайте сертификат CA

В Safari откройте именно HTTP-адрес:

[http://myapp.test/rootCA.crt](http://myapp.test/rootCA.crt)

Если `Domain` изменён, замените имя в ссылке. Разрешите загрузку профиля.

Используется HTTP, поскольку доверие к CA на телефоне ещё только настраивается. Публичный сертификат CA не содержит закрытого ключа.

Текущий Caddyfile обслуживает HTTP по имени приложения. Подстановка IP в URL вместо `myapp.test` не является предусмотренным способом скачивания.

Если необходимо установить сертификат **до изменения DNS**, сначала вручную перенесите на телефон файл `.local/public/rootCA.crt`, например вложением в собственное письмо, и откройте его для установки. Затем выполните установку, включите доверие и настройте DNS по шагу выше.

### 4. Установите профиль сертификата

После загрузки:

1. Откройте **Настройки**.
2. Выберите **Профиль загружен**, если этот пункт появился.
3. Либо откройте **Основные → VPN и управление устройством** и выберите загруженный профиль с сертификатом mkcert.
4. Нажмите **Установить**, введите код-пароль iPhone и подтвердите установку.

Установите профиль сразу после скачивания. Если загруженный профиль исчез, скачайте файл повторно. [Официальная инструкция Apple по установке профиля](https://support.apple.com/en-us/102400).

### 5. Включите полное доверие

Установка профиля сама по себе не включает доверие для HTTPS.

Откройте **Настройки → Основные → Об этом устройстве → Доверие сертификатам**. Включите полное доверие для установленного корневого сертификата mkcert и подтвердите действие.

Устанавливайте CA, созданный для вашего стенда. [Официальная инструкция Apple по доверию сертификатам](https://support.apple.com/en-us/102390).

### 6. Откройте сервис на iPhone

Откройте в Safari:

[https://myapp.test/](https://myapp.test/)

Ожидаемый результат — целевой сервис доступен по HTTPS без предупреждения о сертификате. Содержимое страницы и доступные действия зависят от сервиса.

Если сайт поддерживает установку PWA, выберите **Поделиться → На экран Домой → Добавить**, затем откройте его через появившуюся иконку. Установку выполняйте с HTTPS-адреса сайта, а не со страницы скачивания сертификата.

## Повторный запуск

Если зависимости, CA, сертификат и правила уже подготовлены:

1. Запустите целевой сервис по его инструкции.
2. Из корня проекта утилит выполните `.\startup.ps1`.

На iPhone проверьте, что Wi-Fi DNS указывает на актуальный `LanIp`. Повторно устанавливать сертификат при каждом запуске не требуется.

Для остановки стенда нажмите **Ctrl+C** в окне `startup.ps1`. Веб-сервер приложения останавливается отдельно.

Если стенд остановлен, его DNS тоже недоступен. Чтобы вернуть обычную работу сети на iPhone, откройте настройки DNS этой Wi-Fi-сети и выберите **Автоматически**. При следующем тестировании снова задайте DNS компьютера вручную.

## Изменение сети и других параметров

Перед изменением параметров остановите стенд через Ctrl+C.

| Что изменилось | Что сделать |
|---|---|
| IP компьютера | Изменить `LanIp`, повторно выполнить `firewall_prepare.ps1` от администратора, запустить стенд и обновить DNS-адрес на iPhone |
| Локальная подсеть | Изменить `LanIp` и `AllowedSubnet`, при необходимости `DnsForwarders`, применить брандмауэр и перенастроить DNS iPhone |
| DNS роутера | Обновить `DnsForwarders` и перезапустить стенд |
| Порт или адрес веб-сервера приложения | Обновить `AppUpstream` и перезапустить стенд |
| DNS-имя | Обновить `Domain`, выпустить сертификат через `mkcert_create.ps1` и перезапустить стенд; при необходимости обновить внешний URL в настройках целевого сервиса |
| Расположение проекта | Повторно применить брандмауэр, чтобы обновить пути к исполняемым файлам; при локальном mkcert также обновить `Path` |
| CA mkcert | Перевыпустить сертификат приложения, повторить `caddy_prepare.ps1` и установить новый CA с доверием на iPhone |

Смена IP или DNS роутера не требует перевыпуска сертификата: он выпущен на имя приложения. Если CA остаётся прежним, повторная установка его сертификата на iPhone при обычном перевыпуске сертификата сайта не нужна.

IP и DNS задаются вручную в `config.psd1`.

## Назначение скриптов

| Скрипт | Что делает | Как запускается |
|---|---|---|
| `startup.ps1` | Подготовка DNS-записи, проверка Caddy, запуск и контроль двух серверов | Основная команда запуска |
| `scripts/env_load_config.ps1` | Читает настройки и экспортирует переменные окружения | Вызывается общим запуском и подготовительными операциями |
| `scripts/mkcert_install.ps1` | Устанавливает локальный CA в хранилища доверия | Отдельная первоначальная подготовка |
| `scripts/mkcert_create.ps1` | Загружает конфигурацию и выпускает сертификат домена | Отдельная подготовительная операция |
| `scripts/caddy_prepare.ps1` | Копирует публичный CA в каталог HTTP-раздачи | Отдельная подготовительная операция |
| `scripts/firewall_prepare.ps1` | Загружает конфигурацию, создаёт или обновляет четыре правила | Отдельно, от администратора |
| `scripts/dns_prepare.ps1` | Формирует `.local/dns/hosts.txt` из окружения | Через `startup.ps1` |
| `scripts/dns_start.ps1` | Запускает CoreDNS в фоне и возвращает объект процесса | Через `startup.ps1` |
| `scripts/caddy_start.ps1` | Запускает Caddy в фоне и возвращает объект процесса | Через `startup.ps1` |

Скрипты запуска серверов рассчитаны на подготовленное окружение. Для обычной работы используйте `startup.ps1`, чтобы обеспечить порядок подготовки и завершение обоих процессов.

## Журналы

Все журналы находятся в `.local/logs`:

| Файл | Содержимое |
|---|---|
| `caddy.log` | HTTP-запросы к HTTP- и HTTPS-сайтам, служебные сообщения и ошибки Caddy |
| `coredns.log` | DNS-запросы, служебные сообщения и ошибки CoreDNS |

Используются два постоянных имени файла. При каждом запуске соответствующего сервера его журнал пересоздаётся: старые записи не сохраняются. Файлы с датой в имени, отдельные файлы stderr и архивы больше не создаются.

Caddy выводит запросы в stdout, а служебные сообщения — в свои стандартные потоки. Скрипты запуска используют стандартное перенаправление Windows `> файл 2>&1`, чтобы объединить вывод и ошибки в одном журнале каждого сервера. Сообщения предварительного `caddy validate` по-прежнему видны в консоли запуска.

Серверы запускаются через скрытые оболочки `cmd.exe`; показанные при запуске PID относятся к этим оболочкам. При остановке `startup.ps1` завершает каждую оболочку вместе с её сервером через `taskkill /T`, чтобы фоновые процессы не оставались работать.

Просмотр запросов Caddy:

~~~powershell
Get-Content .\.local\logs\caddy.log -Tail 10 -Wait
~~~

Просмотр журнала CoreDNS:

~~~powershell
Get-Content .\.local\logs\coredns.log -Tail 20 -Wait
~~~

Caddy фиксирует проходящие через него запросы. Сообщения `console.log` приложения и запросы телефона напрямую к отдельному backend требуют собственных средств диагностики.

## Типовые проблемы

### Исполняемый файл или mkcert не найден

Проверьте наличие `tools\caddy\caddy.exe` и `tools\coredns\coredns.exe`. Для mkcert выполните `Get-Command mkcert`. После изменения `Path` откройте новое окно PowerShell.

### mkcert сообщает об ошибке Java cacerts

При настроенном `JAVA_HOME` mkcert может пытаться установить CA также в Java. Ошибка доступа к `cacerts` относится к этому хранилищу и не доказывает отсутствие доверия в Windows.

Если стенду требуется только системное хранилище, выполните установку в отдельном временном окне PowerShell:

~~~powershell
$env:TRUST_STORES = 'system'
.\scripts\mkcert_install.ps1
~~~

После этого закройте это окно. Для Java-backend необходимость доверия настраивается отдельно. [Настройка хранилищ mkcert](https://github.com/FiloSottile/mkcert#supported-root-stores).

### DNS не отвечает или имя не найдено

Проверьте:

- что `startup.ps1` продолжает работать и CoreDNS успел запуститься;
- актуальность `LanIp` и запись в `.local/dns/hosts.txt`;
- ответы `nslookup` с явным указанием DNS-сервера;
- правило брандмауэра и доступ устройств друг к другу;
- DNS выбранной Wi-Fi-сети iPhone, влияние VPN и DNS-профилей.

`NXDOMAIN` означает, что сервер ответил «имя не существует». Отсутствие ответа означает проблему доступности сервера или обработки запроса — это разные ситуации.

### Порт уже занят

Проверьте слушателей:

~~~powershell
Get-NetTCPConnection -State Listen |
    Where-Object { $_.LocalPort -in @(53, 80, 443) } |
    Select-Object LocalAddress, LocalPort, OwningProcess

Get-NetUDPEndpoint -LocalPort 53 |
    Select-Object LocalAddress, LocalPort, OwningProcess
~~~

UDP-порт 53 может занимать служба ICS. Сначала определите процесс и назначение службы. ICS может требоваться WSL2; не отключайте её без выяснения назначения. [Описание зависимости WSL2 от ICS](https://learn.microsoft.com/en-us/windows/wsl/troubleshooting#wsl-2-errors-when-ics-is-disabled).

Перед повторным запуском остановите предыдущий экземпляр стенда штатно.

### Caddy завершился или приложение отвечает 502

Посмотрите `.local/logs/caddy.log`. При 502 проверьте запуск приложения, порт в `AppUpstream` и доступность адреса из `AppUpstream` на компьютере.

Успешная проверка Caddyfile подтверждает конфигурацию, но не доступность самого приложения.

### Safari предупреждает о сертификате

Проверьте имя в адресе, сертификат для этого имени и полное доверие к правильному CA на iPhone. Сертификат приложения и установленный на телефон CA должны относиться к одному центру сертификации. Для скачивания CA используйте HTTP-адрес.

### Нужно скачать CA до настройки DNS

Передайте `.local/public/rootCA.crt` на телефон файлом и установите его. Для открытия `https://myapp.test/` настройка локального DNS всё равно потребуется.

### Backend на localhost или через VPN

`AppUpstream` задаёт веб-сервер приложения. Стенд передаёт ему запросы к `myapp.test`, но не переписывает абсолютные адреса API внутри приложения.

Если браузер iPhone обращается к `localhost` как к API, он ищет сервер на самом телефоне. Для локального backend нужен маршрут через компьютер: существующий прокси приложения либо отдельная настройка API-проксирования. Доступ к корпоративному backend зависит от того, кто выполняет запрос — телефон или сервер на компьютере.

### Предупреждение о форматировании Caddyfile

Это предупреждение не препятствует работе. Отформатировать конфигурацию можно из корня проекта:

~~~powershell
.\tools\caddy\caddy.exe fmt --overwrite .\tools\caddy\Caddyfile
~~~

Обычные сообщения `caddy validate` о запуске и завершении внутренних компонентов относятся к проверке. Ориентируйтесь на `Valid configuration`, состояние процессов и фактические DNS/HTTPS-запросы.
